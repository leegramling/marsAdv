# Build a Rust + Axum + Svelte Text Adventure

Create a small, clean starter project for a browser-based text adventure game set in a partially constructed Mars silo.

The primary purpose of this project is for me to learn Rust. Keep the Rust code straightforward, idiomatic, and easy to understand. Do not over-engineer the architecture or introduce complicated frameworks, ECS systems, databases, authentication, or unnecessary abstractions.

Use:

* Rust, current stable edition
* Axum for the backend HTTP server
* Tokio for the async runtime
* Serde / serde_json for JSON
* Svelte with TypeScript for the frontend

# Game concept

The game is called:

**ARES SILO 7**

It takes place on Mars in a large underground habitat and industrial silo that is still under construction.

Construction robots have begun behaving erratically. The player wakes during an emergency and must explore the facility, diagnose failures, repair systems, seal doors, restore utilities, and eventually determine why the robots are behaving incorrectly.

The initial prototype should only contain three rooms:

1. Control Room
2. Water Pump Room
3. Robot Bay

The initial gameplay progression is:

```text
CONTROL ROOM
     |
     | south
     v
WATER PUMP ROOM
     |
     | east
     v
ROBOT BAY
```

The Control Room initially contains a wrench.

The player must:

1. Look around.
2. Take the wrench.
3. Travel south to the Water Pump Room.
4. Inspect the damaged water pump.
5. Repair the pump using the wrench.
6. Travel east to the Robot Bay.
7. Observe the malfunctioning construction robots.

Do not implement a large story beyond this yet.

# Architecture

The Rust server owns the authoritative game state.

The Svelte application is a UI for displaying the game and sending commands.

Conceptually:

```text
                 Browser
              Svelte / TS
                   |
                   | HTTP / JSON
                   v
                 Axum
                   |
                   v
             Command Parser
                   |
                   v
                 Game
              /        \
          Player       World
                       /   \
                    Rooms  Systems
```

Do not duplicate game rules in TypeScript.

For example, Svelte should not determine whether the player can move east or whether the wrench can repair the pump.

Svelte sends commands such as:

```text
take wrench
```

and Rust determines what happens.

# Rust game model

Start with simple Rust structures and enums.

Something approximately like:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum Location {
    ControlRoom,
    PumpRoom,
    RobotBay,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum Item {
    Wrench,
}

struct Player {
    location: Location,
    inventory: Vec<Item>,
}

struct Pump {
    damaged: bool,
    running: bool,
    pressure: f32,
}

struct Game {
    player: Player,
    pump: Pump,
    wrench_location: Option<Location>,
    turn: u32,
}
```

These are suggestions rather than mandatory exact definitions.

Prefer owned data rather than putting references/lifetimes inside the game structures.

I am learning Rust, so favor clear ownership over clever abstractions.

# Game command execution

Have the game execute parsed commands through something conceptually similar to:

```rust
impl Game {
    fn execute(&mut self, command: Command) -> GameResponse {
        // ...
    }
}
```

Create a serializable response structure.

For example:

```rust
#[derive(Serialize)]
struct GameResponse {
    message: String,
    location: String,
    inventory: Vec<String>,
    turn: u32,
}
```

You may add useful fields such as:

```rust

```

but keep the response compact.

# Pump puzzle

The Water Pump Room contains a damaged pump.

If the player types:

```text
inspect pump
```

before repairing it, return something similar to:

```text
Pump 3 is vibrating violently.

The outlet pressure coupling has partially separated.
It looks like it could be tightened with a wrench.
```

If the player attempts:

```text
repair pump
```

without the wrench:

```text
You need a tool to tighten the damaged coupling.
```

If the player has the wrench:

```text
You tighten the pressure coupling.

The violent vibration slowly subsides.

Pump 3 returns to normal operation.
```

Then set:

```rust
pump.damaged = false;
```

The important part is that this is represented as actual Rust game state, not merely different text.

# Turn system

Increment:

```rust
game.turn
```

after successful game commands.

Keep the turn system simple.

When the pump is damaged, pressure can increase slightly each turn.

For example:

```rust
if self.pump.damaged {
    self.pump.pressure += 2.0;
}
```

Do not implement game-over pressure behavior yet.

This is simply to demonstrate how the world can evolve independently of player movement.

# Axum API

Create a minimal REST API.

For example:

```text
POST /api/game/new
POST /api/game/command
GET  /api/game/state
```

`POST /api/game/new`

creates/resets the game.

`POST /api/game/command`

accepts:

```json
{
    "command": "take wrench"
}
```

and returns something like:

```json
{
    "message": "You pick up the wrench.",
    "location": "Control Room",
    "inventory": ["Wrench"],
    "turn": 2,
    "available_exits": ["south"]
}
```

For this prototype it is acceptable for Axum to maintain one game instance in memory using something simple such as:

```rust
Arc<Mutex<Game>>
```

or:

```rust
Arc<RwLock<Game>>
```

Explain briefly why you selected one.

Do not add a database.

Do not add user accounts or multiple-player sessions yet.

The main UI should contain:

* game title
* current location
* turn number
* scrolling transcript/history
* inventory
* available exits
* command text input
* Restart Game button

When the player enters a command:

1. Add the command to the transcript.
2. Send it to Axum.
3. Receive the JSON response.
4. Add the response message to the transcript.
5. Update location, inventory, exits, and turn.
6. Clear the command input.
7. Return focus to the command input.
8. Scroll the transcript to the newest entry.

Allow Enter to submit the command.

# Separation of responsibilities

Keep the layers approximately:

```text
Svelte
    UI and user interaction
        |
        v
Axum
    HTTP boundary
        |
        v
Command parser
    text -> Command
        |
        v
Game
    rules and state changes
        |
        v
World
    rooms, items, systems
```

In particular:

**The game should be playable without depending on Svelte-specific logic.**

This will make it possible later to add another interface, such as a terminal client, without rewriting the game rules.
